## Database and deployment

Production was verified as V82 with no failed Flyway records before packaging.
Candidate adds V83 shared team definitions, V84 rider credentials, V85 Soko
order destination snapshots and V86 durable notification/receipt metadata.
The first installation applied V83–V86 but failed Hibernate validation because
V86 used camelCase rather than the runtime snake_case physical column names.
Its automatic JAR rollback restored the prior healthy backend. V87 is an
additive compatibility correction: it preserves V86's checksum and columns,
copies existing values into the mapped columns, and adds their unique/query
indexes. No columns or customer records are deleted. The release rehearsal now
also validates Notification/SMS mappings against the migrated schema rather
than relying only on Flyway execution. Retry preflight requires V86, then V87.
V85's legacy backfill freezes the currently configured store receiving account;
it is not evidence of the historical payment's actual recipient. Existing
invoice/payment records remain authoritative. No financial status is fabricated.

The release-only Flyway test passed V83–V86 and validation on MySQL 8.4 in
`slickhood_rehearsal_release_20260915_verified82`. It imports schema only from
the existing local V82 rehearsal database, whose history and V82 conditional-rule
and delivery-recovery columns were verified before copying. The ambiguous legacy
`production-v80-schema.sql` fixture was not used as release evidence: an initial
V80-baseline attempt failed on existing V81 tables, while V82 columns were missing.
A fresh production-schema export was blocked by safety review and
was not performed. This rehearsal is not a claim of a fresh production clone.

The deployment workflow requires dependency preflight before and after,
host-local protected primary/audit database backup archives and checksums,
clean immutable build revisions, rollback JAR/front-end directories, readiness
and deployed-revision verification. Database recovery is forward-only unless
an explicit recovery operation is separately authorised. Credentials remain
in their existing protected locations; none are packaged in source archives.
